## 2026-10-18 通知请求契约校正

- 用户报告 `06:53:12Z`：浏览器上下文为 `fetch_rejected_after_request_observed`，请求钩子已观察、响应事件未观察；独立 `noticeProbe` 仍为 `not_attempted`。这确认页面读取层被拒绝，但没有 HTTP 状态证据，不能标记为接口 403。
- 参考 MIT 公开项目 Xuexitong-mcp，并核对其通知接口实现：固定入口为 `notice.chaoxing.com/pc/notice/getNoticeList`，请求为 POST 表单；原探针用 `notice.xuexitong.com` + GET，与该公开契约不符。
- 第二个公开项目 auto-homework-collector 也使用同一主机、路径和 POST 表单；其 `type=2`/当前年份是作业考试筛选变体，不采用，以免缩小通用通知范围。不需要手动伪造 `Origin`/`Referer`。
- 已将独立 HTTP 读取与浏览器上下文探针同步为 POST 表单，并统一 15 个表单字段；首请求游标为空。保留只读一页、不跟随重定向、不自动重试、不记录 Cookie/请求正文/响应正文的边界。
- 解析器现在识别接口顶层显式失败标记为 `api_rejected`，不会把失败响应误报为空通知列表。
- 独立 OPTIONS 检查返回 HTTP 302，且未观察到 CORS 允许头；这与跨域页面读取被拒绝相符，但不能证明当次表单 POST 一定触发了预检。浏览器探针改为 `no-cors` opaque 请求，使诊断不依赖页面读取响应；opaque 结果仍不能提供状态码，需用独立 HTTP 读取确认。
- 请求契约交叉核对不等于响应解析器兼容：auto-homework-collector 按通知 `content` 文本解析，而当前解析器按 `extendParam.cparams.funConfig` 识别作业通知。真实响应字段仍需通过本地结果类别验证，不导出原始正文。
- 报告 `03:10` 和 `04:00` 是旧 GET 契约下生成的历史诊断，不代表修正后 POST 的结果。仍需用户启动新构建、完成官方登录后主动执行一次探针，才能验证真实账号响应。
- 参考源码：[Xuexitong-mcp](https://github.com/DanMo661/Xuexitong-mcp/blob/main/xuexitong_mcp/client.py)、[auto-homework-collector](https://github.com/men-shen/auto-homework-collector/blob/7c266cb7f242c1b9f89a81a417539e7aa21c26a7/crawler/crawler.py)。只参考公开请求契约，未复制其代码、会话、登录、重试或分页实现；该社区接口不是官方 API 保证。

## 通知接口响应细分

- 本轮根据用户反馈“能登录但是抓不到请求”收窄了诊断差异：全局勾选项只计响应状态类别，并非请求明细。报告 03:10 的 `responseCategories` 有 2xx/3xx 计数，说明窗口观察到响应，但无法指出具体接口；同份报告浏览器内探针为 `not_attempted`，独立通知旧版 GET 收到 302 官方认证域重定向。
- 浏览器内探针现在仅对固定通知 URL 的 Fetch 临时启用 `WebResourceRequested` 请求钩子，并单独记录请求钩子、响应事件是否观察到；不保存具体请求数据。报告升级至 schemaVersion 4。未观察到事件仍不证明服务器未收到，响应状态也不保证唯一归因于这一次 Fetch。
- 用户报告官方登录成功；提供的 schemaVersion 1 报告记录人工确认课程、作业和提交状态可见，但通知读取结果为 authentication_or_redirect，不能将其解释为没有作业。
- 新版分别报告 unauthorized（401）、forbidden（403）、redirect_received（3xx）；保留其他响应的 HTTP 状态码。
- 重定向仅分类为官方认证域名、同域、其他官方域、外部域、HTTP、外部协议、异常地址等，不跟随，不导出原始 Location、路径、查询参数或凭据。
- 导出报告 schemaVersion 4，noticeProbe.http 包含 StatusCode 和 RedirectCategory；noticeProbe.browserContext 记录请求/响应观察布尔值、Fetch 状态、响应类型和验证窗口内观察到的接口状态码；没有响应状态时为 null。
- 隔离输出构建 0 警告／0 错误；本轮 15 项策略、75 项通知解析与模拟 HTTP、8 项导航类别检查通过，共 98 项。
- 本轮未访问用户账号。真实失败状态码、重定向类别及跨域会话原因仍需用户主动读取后验证；本轮不是登录会话修复。
- 新增“浏览器内验证通知接口”诊断：通过当前官方页面上下文发送固定接口请求，不读取正文、不跟随重定向；真实账号结果仍待用户主动验证，CORS 拒绝时可能只能得到不完整证据。历史记录中的 GET 与当前 POST 契约不是同一次请求。

## 2026-10-18 继续修补

- WebView 消息现在校验 JSON 类型、消息种类、nonce 和状态码范围；同源但格式错误的消息会被忽略，不再让异常从事件回调冒出。
- 浏览器上下文探针的脚本等待绑定页面取消；20 秒超时单独记为 `cancelled_or_timeout`，不会误记为普通探针错误。接口响应事件仍只作验证窗口内观察，不能归因到某一次 fetch。
- 全局网络状态计数在缺少响应视图时跳过该事件；不改变导航白名单或报告字段。
- 使用项目内 SDK 的隔离输出构建：主程序与 ProbeChecks 均为 0 警告／0 错误，15 项策略、75 项通知解析与模拟 HTTP、8 项导航类别检查通过，共 98 项；ProbeChecks 已运行通过。默认 `bin` 输出仍被当前验证窗口进程占用，未强制终止。
